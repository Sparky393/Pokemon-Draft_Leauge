Neon outbound-transfer optimization — local implementation report

Implementation and validation were first completed locally. The user subsequently authorized a tested branch and merge to main under the Sparky393 account. No production database connection, production data operation, schema migration, dependency change, or deployment-configuration change is part of this work. Integration preserves the newer main-branch reset-password security fix and source formatting. Tests and browser actions used disposable in-memory H2 databases. The pre-existing untracked `.agents/` and `skills-lock.json` were left unchanged.

All measured read endpoints selected zero Base64 image payload columns after optimization. The previous status poll selected the full image field for all 16 teams, despite returning only a small JSON response. A closed-room revision takes two SELECTs including authorization once at least one pick exists; before the first pick it additionally reads only IDs/positions to detect commissioner order edits. Revealed lineups and nonempty draft picks require their targeted Pokémon/name batch, so counts can differ from the empty-lineup/zero-pick fixture.

Browser measurements confirm one dashboard request at initial login (previously two) and one full draft request per render (previously three). An unchanged status does not refetch the draft. Paused rooms switch to the idle revision; reopening renders once without adding a longer backoff. Finalized rooms stop both draft polling paths. A full schedule already loaded by the page is filtered locally; a filtered re-entry requests only that scope.

**Transfer estimates, distinguished from measurements**

Neon measures PostgreSQL outbound client traffic, rather than the size of Render's HTTP response. See [Neon's network-transfer documentation](https://neon.com/docs/introduction/network-transfer).

Base64 uses `4 × ceil(raw_image_bytes / 3)` bytes. With 16 logos of 100 KiB each, one all-team query previously returned about 2.08 MiB of image strings alone. At 720 five-second polls per tab-hour, excluding those image strings avoids approximately **1.46 GiB of logo payload per visible draft tab-hour in that illustrative fixture**. Normal logo downloads are still necessary and keep their existing browser cache. Actual savings depend on real logo sizes, active tabs, and traffic; if no logos exist, this particular component saves little.

The all-roster endpoint removes 16 complete Pokémon-pool result sets and replaces them with one batch of rostered Pokémon. Initial schedule rendering with All Weeks still legitimately requires the full schedule. A one-game week/team view can restrict the matchup result from 80 seeded games to one, plus only the two participating teams and relevant submissions; this is a row-count estimate for that view, not an application-wide percentage.

No production outbound-byte percentage is claimed. Query-count reduction is not equivalent to byte reduction: excluding image text can dominate even when the SELECT count changes only modestly. PostgreSQL protocol overhead, real row widths, concurrent requests, and traffic mix were not measured. No `pg_stat_statements` extension was installed, reset or queried.

**Limits and pre-existing gaps**

- Production PostgreSQL execution plans and actual Neon wire bytes remain unmeasured. Validation used H2 and the real application browser flows, not a production connection. Queries use JPA/HQL rather than new PostgreSQL-specific SQL or database objects.
- Histories remain complete for compatibility. Journal caching is capped at 5,000 rows; larger histories fall back to fresh full reads rather than truncating results. Bid histories and notifications remain unbounded by design because adding pagination would change the current user experience; batching eliminates the unrelated catalogue reads and per-bid name-query pattern.
- Application journal records are append-only or removed during reset. Their count/latest-ID revision invalidates immediately for those operations. An out-of-band edit to an existing journal description that preserves count/latest ID can remain cached for at most 30 seconds. This cache does not govern active drafts, bids, budgets, ownership, or permissions.
- Team metadata constructors return partial read objects to retain existing Java/JSON types; they must not be passed to `save()`. Updated callers either use them read-only or perform explicit targeted branding updates. Less-frequent existing mutation paths still load full Team entities where preserving all fields is safer than broadening the change; no automatic schema/bytecode enhancement is required.
- The baseline contains legacy trade UI functions referring to `/api/trades` and `/api/flow/trades`, but no controller mappings for these routes, and the free-agency dispatcher does not invoke its trade renderer. This pre-existing routing gap was not expanded into a new feature. The affected trade service behavior is verified by integration tests.

For a later approved production validation, compare hourly Neon transfer and request rates before/after under similar traffic, and inspect existing read-only `pg_stat_statements` calls/rows if available. These statistics rank frequency and returned rows, not exact bytes. No production validation or deployment is part of this local change.
